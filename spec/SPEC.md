## Document Structure

Every OAP file:

```yaml
oap_version: "0.1"        # REQUIRED. Spec version.
kind: Workflow             # REQUIRED. One of: Workflow, AgentProfile, WorkflowTemplate.
metadata:                  # REQUIRED.
  name: my-workflow        # REQUIRED. Pattern: ^[a-z][a-z0-9-]*$
  description: ...         # OPTIONAL.
  labels: { team: infra }  # OPTIONAL. String key-value pairs.
```

Runtimes MUST reject documents with missing `oap_version`, `kind`, or `metadata.name`.

## Workflow Execution Model

Three modes. A workflow uses exactly one.

| Mode | Field | Who builds the DAG |
|---|---|---|
| Static flat | `tasks` | You. Declared in YAML. |
| Static phased | `phases` | You. Grouped and ordered in YAML. |
| Dynamic | `planning` | The model. Generated at runtime by a planner agent. |

### Static tasks

Tasks form an implicit DAG via `needs`. A task runs when ALL dependencies complete (unless `any_of: true`, then ANY).

```yaml
tasks:
  - name: a
    ...
  - name: b
    needs: [a]       # runs after a completes
  - name: c
    needs: [a]       # runs after a completes (parallel with b)
  - name: d
    needs: [b, c]    # runs after both b AND c complete
```

Tasks with no `needs` are roots. They run immediately.

### Phases

Phases are **ordered groups**. Phase N+1 starts only after all tasks in phase N complete.

```yaml
phases:
  - name: plan
    tasks: [...]     # all must complete before 'execute' starts
  - name: execute
    tasks: [...]
  - name: review
    tasks: [...]
```

**Cross-phase `needs`**: A task in phase N+1 MAY reference a task in phase N via `needs`. It MUST NOT reference a task in a later phase. Runtimes MUST validate this at parse time.

**Combinations**: `tasks` and `phases` are mutually exclusive. `planning` can be combined with `tasks` (seed tasks run first, planner adds more). The schema enforces this via `anyOf`.

### Dynamic planning

When a workflow has `planning`, the DAG is generated by a model at runtime. You define agents, constraints, and a goal. The planner agent builds the task graph.

```yaml
agents:
  - name: planner
    model_tier: frontier
    persona:
      role: Technical lead and project planner
  - name: worker
    model_tier: fast
    tools: [shell, file_editor]

planning:
  agent: planner
  goal: "Fix the authentication bug described in issue #42"
  constraints:
    max_tasks: 10
    max_depth: 3
    allowed_agents: [worker]
    require_approval: true
  replan_on_failure: true
```

**How it works:**

1. Runtime sends the `goal` and agent definitions to the planner agent
2. Planner generates a task array (same schema as static `tasks`)
3. If `require_approval: true`, runtime pauses for human review of the plan
4. Runtime validates the generated tasks against task.schema.json
5. Runtime executes the DAG exactly like static tasks
6. If a task fails and `replan_on_failure: true`, the planner gets the failure context and can adjust the remaining DAG

**Rules:**
- Generated tasks MUST conform to task.schema.json
- Generated tasks MUST only reference agents in `allowed_agents` (or all agents if omitted)
- `max_tasks` and `max_depth` are hard limits. Runtime MUST reject plans that exceed them.
- The planner agent itself does not appear in the generated DAG. It runs before the DAG.
- A workflow MAY have both `planning` and `tasks`. If both are present, `tasks` run first (as setup/seed tasks), then the planner generates additional tasks that can reference the seed tasks via `needs`.

### Conditional execution

```yaml
when: tasks.triage.outputs.severity == "critical"
```

If `when` evaluates to false, the task is **skipped**. Skipped tasks:
- Produce `null` for all outputs
- Do NOT trigger `on_failure`
- Downstream tasks that depend on a skipped task still run (they see `null` outputs)
- Use `when` on downstream tasks to handle the skip case

### Agent assignment

Every task MUST name an `agent` (or a `workflow_ref` for sub-workflow delegation). The agent MUST be defined in the workflow's `agents` array. Runtimes MUST reject tasks referencing undefined agents.

**Agent names**: In a Workflow, every agent MUST have a `name` (enforced by the workflow schema). In an AgentProfile, `name` is optional — the profile name comes from `metadata.name`.

## Model Resolution

Two ways to specify which model an agent uses.

### Explicit model

```yaml
agents:
  - name: planner
    model: claude-sonnet-4
```

Direct model identifier. Vendor-specific. Supports `${ENV_VAR}` interpolation.

### Model tiers (portable)

```yaml
agents:
  - name: planner
    model_tier: frontier     # best available, for planning
  - name: worker
    model_tier: fast         # cheap and quick, for mechanical tasks

runtime:
  model_tiers:
    frontier: claude-sonnet-4
    standard: claude-haiku
    fast: gpt-4o-mini
    embedding: text-embedding-3-small
```

| Tier | Intent | Example use |
|---|---|---|
| `frontier` | Best available model. Highest quality. | Planning, architecture, complex reasoning |
| `standard` | Balanced cost and quality. | General development, code review |
| `fast` | Cheapest viable model. | Linting, formatting, well-defined edits |
| `embedding` | Vector/search model. | Semantic search, RAG |

**Resolution order:**

1. `model` on the agent (wins if set)
2. `model_tier` resolved against `runtime.model_tiers`
3. `model_tier` resolved against runtime defaults (runtime MAY have built-in tier mappings)
4. If neither `model` nor `model_tier` is set, runtime picks a default

**Rules:**
- `model` and `model_tier` are mutually exclusive on a single agent. Runtimes SHOULD warn if both are set; `model` wins.
- `runtime.model_tiers` is optional. Runtimes MAY accept tier mappings via env vars, CLI flags, or config files.
- Tiers are a portability feature. A workflow using only `model_tier` runs on any runtime with any provider without changes.

### Model Fallback

`model_fallback` is an ordered list of alternatives tried when the primary model is unavailable or returns a rate-limit error.

```yaml
agents:
  - name: analyst
    model: claude-sonnet-4
    model_fallback:
      - claude-haiku
      - tier:standard
      - gpt-4o
```

**Fallback chain rules:**
- Entries are tried in order. First successful response wins.
- Entries can be explicit model identifiers (e.g. `claude-haiku`) or tier references (`tier:fast`).
- Tier references in fallbacks resolve against `runtime.model_tiers` using the same lookup as `model_tier`.
- If the chain is exhausted (all entries fail), the task fails with a `model_unavailable` error.
- Runtimes SHOULD surface which fallback model was used in task metadata.

## Agent Profile Merging

When a workflow declares `agent_profile`, the profile provides defaults for all agents:

```yaml
agent_profile: ./profiles/senior-engineer.oap.yaml

agents:
  - name: backend-1
    # Inherits persona, policies, lifecycle from profile
    # Inline fields override profile defaults
    tools: [shell, file_editor]  # overrides profile tools
```

**`principles`**: An array of high-level directives injected into the agent's context window before every task. Unlike `persona.constraints` (behavioral rules the runtime can enforce mechanically), principles are philosophical guidelines — things like "prefer reversible changes" or "always leave code cleaner than you found it." Runtimes inject them as text; there's no programmatic enforcement.

**Merge rules:**
- Scalar fields (model, instructions): inline replaces profile
- Object fields (persona, subagent_strategy, permissions, budget): inline fields override profile fields, unset fields inherited
- Array fields (tools, principles, policies): inline replaces profile (no merge)
- To extend an array, repeat the profile values plus your additions

## Output Types

### Simple (untyped)

```yaml
outputs: [root_cause, affected_files]
```

Untyped outputs are strings. Runtimes treat them as opaque string values. No validation beyond existence.

### Typed

```yaml
outputs:
  - name: severity
    type: string
    enum: [low, medium, high, critical]
    required: true
  - name: line_count
    type: number
```

Runtimes MUST validate typed outputs against their declared type and enum. If a required output is missing, the task fails.

**Type mapping:**

| OAP Type | JSON Type | Notes |
|---|---|---|
| `string` | string | Default if untyped |
| `number` | number | Integer or float |
| `boolean` | boolean | |
| `file_list` | array of strings | File paths |
| `markdown` | string | Rendered as markdown by UIs |
| `json` | object | Arbitrary structured data |
| `action` | string | Represents an action to take |

## Interpolation Resolution Order

When resolving `${}` expressions, runtimes check sources in this order:

1. `${secrets.<name>}` — Secret references (from permissions.secrets)
2. `${params.<name>}` — WorkflowTemplate parameters
3. `${tasks.<name>.outputs.<key>}` — Upstream task outputs (runtime only)
4. `${metadata.<field>}` — Document metadata
5. `${ENV_VAR}` — Environment variables (from runtime.env, then system env)

First match wins. If no match and the value is required, runtime MUST error.

## Policy Evaluation

Policies are evaluated at specific lifecycle points based on their `trigger`:

1. **At task start**: Policies with triggers referencing `task.*` are checked
2. **At task completion**: Policies with `trigger: task.completing` are checked
3. **On events**: Policies with `trigger: event.*` are checked when the event fires

**Evaluation order**: Policies are evaluated in the order they appear in the array. First `hard` gate failure stops the task.

**Policy sources** (applied in this order, later overrides earlier):
1. `agent_profile` policies
2. Agent-level `policies`
3. Task-level policies (if any)

## MCP Servers

OAP does not replace MCP (Model Context Protocol). It sits one layer above — controlling which agents can reach which MCP servers and which tools they can call.

### Declaring servers

```yaml
mcp_servers:
  - name: github
    transport: stdio
    command: npx
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: ${secrets.github_token}
    description: GitHub repository search, file content, PR management.
    startup_timeout: 15s

  - name: postgres
    transport: stdio
    command: npx
    args: ["-y", "@modelcontextprotocol/server-postgres", "${secrets.db_url}"]

  - name: internal-api
    transport: sse
    url: https://mcp.internal.corp/sse
    auth:
      type: bearer
      token: ${secrets.api_token}
```

Three transports are supported: `stdio` (subprocess), `sse` (server-sent events over HTTP), `http` (plain HTTP/JSON-RPC).

Runtimes MUST start all declared `mcp_servers` before executing any tasks.

### Per-agent access

Agents declare which servers they can access in `permissions.mcp`:

```yaml
agents:
  - name: researcher
    permissions:
      mcp:
        servers: [github, postgres]         # access these two servers
        allow_tools:                         # only these specific tools
          - github:search_repositories
          - github:get_file_contents
          - postgres:query
        deny_tools:                          # explicitly blocked even if allow_tools extends
          - postgres:execute_write

  - name: orchestrator
    permissions:
      mcp:
        servers: ["*"]                       # all declared servers
        # no allow_tools = unrestricted on permitted servers
        deny_tools:
          - github:delete_repository

  - name: reporter
    permissions:
      mcp:
        servers: [slack]
        # no allow_tools, no deny_tools = full access to slack server
```

### Rules

- `servers: []` or omitting `mcp` entirely = no MCP access for this agent
- `servers: ["*"]` = access to all servers declared in `mcp_servers`
- `allow_tools` format: `"server_name:tool_name"` (e.g. `"github:search_repositories"`)
- `deny_tools` takes precedence over `allow_tools` (same as filesystem deny)
- If `allow_tools` is set, agent MUST NOT call any tool not in the list (even on a permitted server)
- Server names in `permissions.mcp.servers` MUST match entries in `workflow.mcp_servers[].name`
- Runtimes MUST enforce MCP permissions. An agent cannot call a tool on a server not in its `servers` list.

## Permissions Enforcement

Runtimes MUST enforce permissions. This is not advisory.

**Filesystem**: Agent's file operations are checked against `allow_read`, `allow_write`, and `deny`. Deny takes precedence over allow. If `filesystem` is not declared, the agent has full access (backward compatible).

**Network**: If `network.allow` is `none`, the agent MUST NOT make network requests. If `restricted`, only `allowed_hosts` are permitted. If `network` is not declared, the agent has full access.

**Shell**: If `shell.allow` is `false`, the agent MUST NOT execute shell commands. `blocked_commands` is a substring match — if any blocked string appears in the command, it is rejected.

**Secrets**: Resolved at workflow start. If a required secret cannot be resolved, the workflow MUST NOT start.

**MCP**: Runtimes MUST only provide a server connection to an agent if the server is listed in `permissions.mcp.servers`. Tool calls outside `allow_tools` (when set) MUST be blocked. `deny_tools` calls MUST be blocked.

## Structured Agent Output

### Why

By default agents produce free-form text. Runtimes may apply heuristic extraction of outputs from embedded ```json blocks, but this is fragile and unportable. When epoch coordination or reliable output interpolation is needed, use `output_format: structured`.

### Contract

When `output_format: structured` is set on an agent, the runtime MUST:

1. **Inject the closing instruction** — append to the agent's task description:

   > When your work is complete, output a fenced code block with language `oap-result` as your LAST output. The block MUST be valid JSON conforming to the TaskResult schema:
   >
   > ````
   > ```oap-result
   > {
   >   "status": "ok",
   >   "summary": "brief description of what was done",
   >   "outputs": { "key": "value" },
   >   "artifacts": ["relative/path/to/file"],
   >   "build_ready": true
   > }
   > ```
   > ````
   >
   > `status` MUST be `ok`, `error`, or `partial`. Include `error` field if status is not `ok`.

2. **Parse the result** — after the agent finishes, find the LAST `oap-result` fenced block in the agent's output. Parse it as the authoritative TaskResult. If no valid block is found, treat as a parse error and set task status to `partial`.

3. **Promote to OAP envelopes** — for each field in the TaskResult:
   - `outputs` scalar values → `signal.output` envelopes (key/value pairs)
   - `artifacts` paths → `signal.artifact` envelopes (registered in file registry)
   - `build_ready: true` → call `epoch.MarkReady()` (equivalent to `build.ready`)
   - `status: error` → emit `lifecycle.task.failed` event

4. **Suppress heuristic extraction** — when an `oap-result` block is found, the runtime MUST NOT additionally apply heuristic JSON extraction from prose. The structured block is the sole source.

### TaskResult Schema

Schema: `schemas/v0.1/task-result.schema.json`

| Field | Required | Description |
|---|---|---|
| `status` | yes | `ok` / `error` / `partial` |
| `summary` | no | Human-readable completion note |
| `outputs` | no | Named output values (maps to task `outputs[]`) |
| `artifacts` | no | Files written/modified (relative to `working_dir`) |
| `build_ready` | no | `true` = agent finished writes, ready for build epoch |
| `error` | when status ≠ ok | Error description |
| `tokens_used` | no | `{input, output}` — self-reported token counts |

### Epoch Integration

Setting `build_ready: true` in the TaskResult is the preferred mechanism over `auto_ack` on `build_policy`. When runtimes parse `build_ready: true`, they MUST call `epoch.MarkReady()` before closing the task. This enables epoch cycles to be driven entirely by agent intent rather than timer-based fallbacks.

```yaml
agents:
  - name: backend-agent
    output_format: structured  # agent will emit oap-result block

workflow:
  build_policy:
    strategy: on_task_complete
    build_command: npm run build
    # auto_ack not needed — agents signal build_ready in their oap-result block
```

### Compatibility

`output_format: stream` (default) preserves existing behavior. Runtimes that do not support structured output MUST ignore the `output_format` field and fall back to heuristic extraction. When a runtime supports `structured` mode for one runtime type (e.g., Claude Code) but not others, it MUST document this in runtime capabilities.

## Budget Enforcement

Three levels, evaluated innermost first:

1. **Task budget** — per-task limit. Checked after each agent turn.
2. **Agent budget** — per-agent limit across all tasks. Checked after each agent turn.
3. **Workflow budget** — global limit. Checked after each agent turn.

When a budget is exceeded:
- `stop`: Agent is halted. Task fails with budget error.
- `fallback`: Agent switches to next model in `model_fallback` chain. If chain exhausted, stop.
- `warn`: Log warning, continue execution.

## Approval Flow

When a task has `approval`:

1. **`before_start`**: Runtime pauses before assigning the task. Sends `request.approval` to `approvers`. Task starts only on approval.
2. **`after_complete`**: Agent completes work. Runtime pauses before marking task done. Sends `request.approval`. Task is marked complete only on approval.
3. **`both`**: Both gates.

If `timeout` expires: runtime executes `on_timeout` (auto_approve, fail, or escalate).

## Sub-Workflow Delegation

A task with `workflow_ref` delegates to another OAP workflow:

```yaml
- name: run-tests
  workflow_ref: ./test-suite.oap.yaml
  description: Run the test suite
  inputs: { test_command: "make test" }
```

The sub-workflow:
- Receives `inputs` as environment variables
- Executes independently with its own agents
- Returns its final task's outputs as this task's outputs
- Inherits parent workflow's `runtime.env` (sub-workflow env overrides on conflict)
- Does NOT inherit parent's `build_policy` or `agent_profile`

## Parallelism

Tasks with no mutual `needs` are parallel-eligible. Four mechanisms restrict parallelism:

1. **Concurrency groups** — Named groups with `max_parallel`. Tasks in the same group compete for slots. See `runtime.concurrency`.
2. **Resource locks** — Named mutexes. A task blocks until all its `resource_locks` are acquired. Acquired in alphabetical order to prevent deadlock.
3. **Agent concurrency** — `agent.max_concurrent_tasks` (default 1). Controls whether an agent can work multiple tasks simultaneously.
4. **Global cap** — `runtime.max_concurrent_agents`. Hard ceiling on total parallel agents.

When tasks compete for a slot: `queue: priority` uses `task.priority` (0-100, higher first), `queue: fifo` (default) uses ready-order.

Full spec: [PARALLELISM.md](./PARALLELISM.md).

## Agent Isolation

Six independent isolation controls:

| Primitive | Scope | What it controls |
|---|---|---|
| `permissions.filesystem` | Per-agent | File read/write access |
| `permissions.network` | Per-agent | Host-level network access |
| `permissions.shell` | Per-agent | Shell command execution |
| `permissions.communication` | Per-agent | Which agents can be messaged |
| `output.visibility` | Per-output | Which agents can read a specific output |
| `runtime.isolation` | Workflow | Process/container boundaries, filesystem/network sharing |

**Communication boundaries**: `can_message`, `can_receive_from`, `can_handoff_to`. Coordinator messages bypass these (coordinator is privileged). Omit for unrestricted.

**Output visibility**: Typed outputs with `visibility: [agent-a, agent-b]` are only consumable by those agents. Runtimes MUST validate at parse time.

**Execution isolation levels**: `shared` (one process), `process` (default, separate processes), `container` (OCI container per agent). When `shared_filesystem: false`, epoch coordination handles merge.

Full spec: [ISOLATION.md](./ISOLATION.md).

## Data Interoperability

### Output contracts

Typed outputs with `schema` define a formal contract:

```yaml
outputs:
  - name: report
    type: json
    schema:
      type: object
      required: [severity, files]
      properties:
        severity: { type: string, enum: [low, medium, high, critical] }
        files: { type: array, items: { type: string } }
    visibility: [lead, reviewer]
```

Runtimes MUST validate outputs against the declared schema.

### Cross-boundary rules

- Sub-workflows (`workflow_ref`) receive only explicit `inputs`. No implicit context leaks.
- Sub-workflows define their own agents, permissions, and isolation. They do NOT inherit from parent.
- Message-based data exchange is subject to `communication` permissions.

## Loop Execution

Loops let a task or phase run iteratively until exit criteria are met or a maximum iteration count is reached.

Full spec: [LOOPS.md](./LOOPS.md).

### Loop on a task

```yaml
tasks:
  - name: implement-and-verify
    agent: coder
    description: |
      Implement the feature. Iteration ${loop.iteration} of ${loop.max_iterations}.
      Previous summary: ${loop.previous_summary}
    outputs:
      - name: tests_pass
        type: boolean
        required: true
      - name: loop_summary
        type: string
    loop:
      max_iterations: 5
      exit_when: "tasks.implement-and-verify.outputs.tests_pass == true"
      on_max_iterations: escalate
      context:
        strategy: fresh
        summary_output: loop_summary
```

The task runs. After it completes, if `exit_when` evaluates false the runtime re-queues it with `loop.iteration` incremented. Loop variables are injected into the next session's description and inputs.

### Loop on a phase

```yaml
phases:
  - name: refine
    loop:
      max_iterations: 3
      exit_when: "tasks.score.outputs.quality_score >= 8"
    tasks:
      - name: draft
        agent: writer
      - name: score
        agent: reviewer
        needs: [draft]
```

All tasks in the phase run each iteration. Exit condition is evaluated after the last task in the phase completes.

### Exit criteria

Exit criteria MUST reference typed, required outputs. Machine-verifiable conditions only.

```yaml
exit_when: "tasks.test.outputs.all_passed == true"    # good
exit_when: "tasks.score.outputs.quality_score >= 8"   # good
exit_when: "tasks.build.outputs.done == true"          # bad — agent can trivially emit done=true
```

### Context strategy

`strategy: fresh` (default) — new agent session per iteration, previous artifacts injected from disk. Avoids context window degradation. Required when `max_iterations > 3`.

`strategy: reuse` — same session continues. Runtimes SHOULD warn when `reuse` and `max_iterations > 3`.

### Iteration variables

Available in task `description`, `inputs`, and `when` expressions during loop execution:

| Variable | Description |
|---|---|
| `loop.iteration` | Current iteration (1-based). |
| `loop.max_iterations` | Upper bound from config. |
| `loop.previous_outputs.<key>` | Named output from the previous iteration. Null on iteration 1. |
| `loop.previous_summary` | Value of `context.summary_output` from previous iteration. |

### on_max_iterations

| Value | Behavior |
|---|---|
| `fail` | Task/phase fails. `on_failure` fires. |
| `escalate` | Runtime pauses, sends `request.approval` to `escalate_to`. |
| `continue_last` | Use final iteration's output, mark status `partial`. |

### Multiple loops in a DAG

Loops are tasks and phases. They compose via `needs` like any DAG node. Sequential, parallel, and chained loops are all valid. Nested loops (loop task inside loop phase) are NOT allowed — runtimes MUST reject them.

### Rules

- `max_iterations` is REQUIRED. Runtimes MUST enforce it as a hard stop.
- `exit_when` is OPTIONAL. When absent, the loop always runs `max_iterations` times.
- Iteration budgets (`budget_per_iteration`) are enforced against all enclosing ceilings.
- Runtimes MUST inject `loop.*` variables when `strategy: fresh`.
- Runtimes MUST reject documents where a task with `loop` is inside a phase with `loop`.

## Extension Mechanism

All schemas support `x-*` prefixed fields:

```yaml
agents:
  - name: backend
    model: claude-sonnet
    x-swarm:
      checkpoint_interval: 60s
      max_tool_calls: 50
```

Rules:
- Keys MUST start with `x-`
- Values MUST be objects (not scalars)
- Runtimes MUST ignore unknown `x-*` fields
- Runtimes MUST NOT require `x-*` fields for core behavior
- Custom message types MUST be prefixed with `x-<namespace>.`
